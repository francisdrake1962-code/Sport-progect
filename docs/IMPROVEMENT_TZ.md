# ТЗ: безопасное улучшение стабильности и функций

Дата: 2026-07-29  
Основание: фактическая сверка кода, тестов, отчётов и внешних замечаний.

## Принципы выполнения

1. Не делать массовый rewrite. Каждая задача — отдельный небольшой PR.
2. Сначала добавить воспроизводящий тест, затем изменить код, затем прогнать
   весь набор тестов, lint и build.
3. Не менять действующий HTTP-контракт без периода совместимости.
4. Любое изменение схемы — только новой versioned migration; существующие
   данные не удалять и не преобразовывать без backup и плана отката.
5. Включать рискованные изменения за feature flag или поэтапно, если это
   влияет на платежи, доступ к видео или учётные записи.

## P0 — целостность платежей и доступов

### PAY-001. Машина состояний подписки

Ввести документированную модель `trial`, `active`, `past_due`, `cancelled`,
`expired`. Поле `plan` (`trial`, `monthly`, `annual`) остаётся независимым от
статуса. Даты доступа хранятся в UTC.

Правила:

- `active` даёт доступ до `subscription_expires_at`;
- `past_due` сохраняет или ограничивает доступ только по явно утверждённому
  grace period;
- `cancelled` сохраняет доступ до даты окончания;
- `expired` и `past_due` после grace period не дают доступ к платному видео;
- событие Stripe `active` восстанавливает локальный статус в `active`;
- `unpaid` не должен безусловно превращаться в `expired`.

Критерии приёмки:

- тесты покрывают все допустимые переходы и запрет недопустимых;
- тесты подтверждают доступ к видео в каждом состоянии;
- API возвращает код статуса подписки и дату, понятные клиенту;
- документация API и интерфейс показывают один и тот же смысл статуса.

### PAY-002. Атомарная обработка webhook

Ввести состояния `received`, `processed`, `failed` у записи webhook либо
отдельную таблицу попыток. Запись события, изменение платежа, подписки и
аудит должны завершаться одной транзакцией.

Критерии приёмки:

- два одинаковых события одновременно приводят к одному бизнес-эффекту;
- ошибка после принятия события оставляет его повторно обрабатываемым;
- повтор Stripe после сбоя завершает операцию;
- нераспознанное событие не меняет доступ;
- добавлены тесты отказа, retry и ручного revoke.

### PAY-003. Единый источник периода подписки

Stripe `current_period_end` — источник истины для рекуррентной подписки.
Локальные 30/365 дней разрешены только для временного fallback или ручного
доступа и должны быть явно помечены.

Критерии приёмки: документировано решение о рекуррентности; тесты не допускают
уменьшения уже оплаченного срока; cancel-at-period-end сохраняет доступ.

## P1 — надёжность, безопасность и поддержка

### OPS-001. Надёжное сохранение и восстановление БД

Заменить прямую запись файла на: export → временный файл в том же каталоге →
flush/fsync → atomic rename. Добавить резервное копирование до миграции и
операционный сценарий restore.

Критерии приёмки:

- интеграционный тест «создать данные → закрыть процесс → открыть → прочитать»;
- тест невалидного/оборванного временного файла не повреждает последнюю БД;
- backup и restore проверяются на копии БД;
- инструкция восстановления находится в документации деплоя.

### OPS-002. Честный CI quality gate

CI должен вызывать `npm run lint`, `npm test -- --runInBand` и `npm run build`
без `continue-on-error`. Вначале устранить или зафиксировать текущие warnings,
чтобы постепенно включить `--max-warnings 0`.

Критерии приёмки: pull request не может быть объединён при ошибке lint, test
или build; обе поддерживаемые версии Node проходят одинаковый набор команд.

### API-001. Единый формат ошибок без поломки клиентов

Для новых и изменяемых endpoints вернуть
`{ success: false, error: { code, message }, requestId }`. На переходный
период сохранить верхнеуровневое `error` для старых клиентов.

Критерии приёмки: ошибки payment, auth и user endpoints имеют стабильные коды;
frontend использует коды, а не английский текст; есть contract tests.

### AUTH-001. Восстановление пароля

Добавить запрос сброса, одноразовый токен с TTL, смену пароля и отзыв активных
токенов. Не раскрывать факт существования email в ответе на запрос сброса.

Критерии приёмки: токен одноразовый и истекает; лимит запросов; письмо не
содержит пароль; старые сессии отклоняются; есть негативные тесты.

### DOC-001. Официальный Payment Flow и обработка ошибок

До включения реальных платежей добавить в `docs/API.md` и
`docs/ARCHITECTURE.md` единую схему: выбор плана → checkout → Stripe →
проверка подписи webhook → идемпотентная транзакция → изменение платежа и
подписки → выдача доступа. Описать сценарии `card_declined`, timeout,
недоступность провайдера, delayed/repeated webhook и ручной revoke.

Критерии приёмки: у каждого сценария есть серверный результат, сообщение для
пользователя, правило retry и тест; документация не обещает поведение, которого
нет в коде.

### DOC-002. Стратегия провайдера и рекуррентности

Зафиксировать Stripe как единственный payment provider первого этапа и
рекуррентную подписку как текущую бизнес-модель. Выделить узкий adapter boundary
в `payment.service`, но не создавать неиспользуемые интеграции YooKassa или
CloudPayments.

Критерии приёмки: ADR не содержит утверждение об отсутствии gateway; cancel,
renewal и refund имеют однозначные владельцы и события Stripe.

### DB-001. Стратегия миграций и rollback

Перед каждой миграцией схемы создавать резервную копию. Зафиксировать, какие
миграции откатываются обратной миграцией, а какие исправляются новой forward
migration. Для существующих пользователей описать преобразование plan/status,
дат доступа и платёжных записей.

Критерии приёмки: migration dry-run проходит на копии production-like БД;
backup/restore проверены; миграция не удаляет платежи; есть runbook и владелец
решения о восстановлении.

### API-003. Машиночитаемые причины отказа в доступе

Не менять HTTP-статус существующих клиентов внезапно. Добавить в ответ на 403
стабильное поле `code`: `SUBSCRIPTION_REQUIRED`, `SUBSCRIPTION_EXPIRED`,
`EMAIL_CONFIRMATION_REQUIRED` или `FREE_LIMIT_REACHED`.

Критерии приёмки: frontend показывает действие по коду; ответы не раскрывают
путь к видео или внутренние данные Stripe; есть contract tests для каждого кода.

## P2 — качество кода и эксплуатация

### ARC-001. Поэтапное подключение service/repository слоёв

После PAY-001/002 перенести только платежный домен в согласованный слой
service/repository. Остальные домены не менять в том же PR.

Критерии приёмки: route содержит HTTP-валидацию/авторизацию/ответ; SQL живёт в
repository; business rules живут в service; регрессионные HTTP-тесты сохранены.

### OBS-001. Полный аудит критичных действий

Логировать после успешного commit: создание checkout, завершение/ошибку
платежа, изменение подписки, grant/revoke и восстановление БД. Не писать в
audit секреты, полные payload Stripe или персональные платёжные данные.

### UX-001. Подписка и платежи в кабинете

Добавить пользователю понятный экран статуса: текущий план, дата доступа,
состояние оплаты, причина ошибки, кнопка повторить попытку и ссылка на
управление биллингом Stripe. Это не должно выдавать доступ по данным браузера:
источник истины — сервер/webhook.

### UX-002. Доставка уведомлений и настройки

Определить один канал первого этапа (email). Добавить подписки на типы
уведомлений, очередь/статусы отправки и экран истории. Web Push — отдельная
будущая задача, не блокирующая email.

### ARCH-001. Актуальная карта архитектуры

Обновить `docs/ARCHITECTURE.md` и `FEATURE_REGISTRY.md`: для каждого домена
указать frontend, endpoint, route, service, repository, таблицы, внешние
интеграции и статус `wired` / `partial` / `planned`. Удалить или пометить как
исторические устаревшие ADR-утверждения.

Критерии приёмки: новая функция не может быть отмечена как готовая без ссылки
на тест; документация проходит проверку ссылок в CI.

### DB-002. Инварианты и границы транзакций

Документировать и проверить уникальность email, прогресса пользователя по
уроку, feedback-политики, внешних payment/webhook IDs и правила foreign keys.
Транзакционно выполнять payment completion, выдачу/отзыв доступа, обновление
прогресса/streak и запись соответствующих событий.

Критерии приёмки: каждая инварианта имеет DB constraint либо явную
транзакционную проверку и негативный тест; гонка не создаёт дубли или частичное
состояние.

### NFR-001. Измеримые эксплуатационные требования

Установить и проверить: p95 API для status/payment, время восстановления из
backup, максимально допустимый размер frontend-ресурсов, допустимое число
ошибок webhook, и успешный deployment smoke test.

Критерии приёмки: значения зафиксированы в документации; CI измеряет build
budget; мониторинг/логи позволяют обнаружить превышение; релиз имеет checklist.

## P3 — оптимизация без изменения бизнес-поведения

- Сжать `hero-poster.jpg`, подготовить responsive WebP/AVIF; сохранить JPEG
  fallback и проверить visual regression.
- Добавлять pagination и выборочные поля на тяжёлые admin списки; не менять
  дефолтный ответ API без совместимого режима.
- Убрать `unsafe-inline` только после переноса inline handlers/scripts в
  bundle; добавлять CSP сначала в report-only режиме.
- Измерить медленные запросы до добавления индексов; не добавлять индексы
  «на всякий случай».

## Обновление документации

До реализации PAY-001 в `docs/API.md`, `docs/ARCHITECTURE.md` и ADR нужно
зафиксировать: Stripe как единственный provider первого этапа, рекуррентную
модель, state machine, оплату/отмену/сбой, миграцию существующих пользователей
и rollback. Устаревшие заявления об отсутствии payment gateway удалить или
пометить историческими.
